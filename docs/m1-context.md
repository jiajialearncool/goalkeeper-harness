# 第1题：减少重复读取和整理开销

本轮范围：先实施前三项优化，保留必要复核，只重新运行 GoalKeeper 的 M1。第2题、其他组和正式评测不启动。

## 实现

1. 恢复前核对实际文件和已通过的阶段证据，提供已验证进度、变化文件及待完成事项。读取文件支持按行读取；当前工作上下文已经包含同版本完整正文时，重复读取返回引用。文件、目标版本改变，或正文已不在工作上下文中时，仍返回正文；模型也可以使用 `force=true` 补读。
2. 每次请求生成较短的工作视图。较旧且成功完成的工具调用和结果一起转为带原文引用的记录；完整运行历史保持不变。失败和未完成调用不做这种处理。保留近期工作以及有限数量的未改变文件正文。摘要输入进一步整理已结束工作中的补丁、读取及回溯材料，自动回溯总正文预算降到1,024 token，显式补读继续遵守原4,096 token限制。
3. 规划时增加要求对应的测试覆盖清单，在已有主调用中完成，不另开规划模型调用。生成指导优先使用共享数据、参数化和批量修改，阶段通过后由程序推进，避免继续润色已满足的工作。清单由模型提出，不能代替独立验收。

必要复核独立保留90秒，另保留原120秒必要检查和交付时间。自动交付必须取得当前文件及目标版本的结构化复核结果。复核超时或缺少结构化结论不能算通过；网络中断后可继续尚未结束的只读复核，已有效的阶段检查不重复执行。

开关 `focused_context_enabled` 和 `final_review_required` 默认关闭，本轮M1启用。原64,000 token工作上下文、压缩触发规则、完整事务分段、分段摘要保存、权限边界不变。

## 检查与收益判定

先运行原检查及新增自动检查，不调用模型。随后使用原封存M1题包、反馈和15项独立评分条件；模型仍为 `gpt-6.1-sol / xhigh`，单次30分钟、100万可观测token，单并发，同一订阅接入。

分别记录：交付及复核结果，读取请求数、返回正文数、同文件同版本同范围的重复正文数，摘要实际模型请求数，执行时间、可观测token及用量完整性。缓存减少正文不等于减少工具请求；文件内容改变后的必要读取不算重复正文。

第一档只是待检验的安排目标：整题17分45秒、34万可观测token，不是承诺值。历史参考为上轮GoalKeeper28分20秒、至少57.56万token；历史Codex13分29秒、30.22万token。不同时间的单次运行只能用来诊断，不能证明稳定持平或领先。

运行记录保存至 `outputs/m1-context`，独立评分输入、原评分规则和原运行记录保持不变。

## 本轮发现的运行缺陷

第一次执行在转入报表阶段时，缩短自动回溯片段的逻辑把检索返回的原始归档编号传给仅接受 `archive:` / `call:` 引用的读取接口，导致程序停止。已补齐归档前缀及对应检查；不改题目、评分规则或任务文件。保留第一次失败及交付快照，再按原已消耗预算从现有进度续跑。修复前后程序版本分开记录，累计消耗不清零，这条记录属于开发验证，不能当成固定版本一次成功的正式对照结果。
